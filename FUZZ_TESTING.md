# Fuzz Testing Strategy

## Goal

Verify correctness as optimizations stack (predictive dispatch, Dyck pairing, eager eviction, SIMD structural scan, memo ring buffer). Each optimization changes a different invariant; testing must catch any of them drifting from correct PEG semantics.

Two complementary approaches: grammar-driven differential testing (valid inputs, correct output) and coverage-guided byte fuzzing (arbitrary inputs, no crashes).

---

## Approach 1: Grammar-Driven Differential Testing

### Architecture

The proc macro generates two implementations from the same grammar:

```rust
#[derive(Parse)]
enum Json {
    #[rule("null")] Null,
    #[rule("[" _ $0 *% (_ "," _) _ "]")] Arr(Vec<Json>),
    // ...
}

// Generated by proc macro:

// 1. Reference parser — textbook PEG, no optimizations
//    - Sequential ordered choice (try each alt, backtrack on failure)
//    - Full tag stack (O(n)), deferred construction
//    - No memo, no dispatch table, no SIMD, no commit points
impl ReferenceParser for Json {
    fn ref_parse(input: &str, pos: usize) -> Result<(usize, Self), Error> { ... }
}

// 2. Optimized parser — all optimizations enabled
//    - Predictive dispatch table
//    - Dyck bracket pairing + commit points
//    - Eager eviction, fused parse+construct
//    - Memo ring buffer for speculative rules
//    - SIMD structural scan
impl ParseImpl for Json {
    fn parse_and_build(
        input: &str, pos: usize, ctx: &mut ParseContext
    ) -> Result<(usize, Self), Error> { ... }
}
```

Same grammar, same proc macro invocation, two code paths. The reference parser is a direct transliteration of PEG semantics — slow but obviously correct. Feature-gated behind `#[cfg(test)]` or `#[cfg(feature = "fuzz")]` so it never appears in production builds.

### Input Generation

The proc macro knows every rule, regex, and literal in the grammar. It generates a random valid input by walking the grammar top-down:

- At each ordered choice: pick a random alternative.
- At each repetition (`*`, `+`, `*%`, `+%`): pick a random count (bounded).
- At each regex terminal: generate a random string matching the regex.
- At each literal: emit the literal.

```rust
// Generated by proc macro
impl GenerateRandom for Json {
    fn generate(rng: &mut impl Rng, depth: usize) -> String {
        if depth > MAX_DEPTH { return generate_leaf(rng); }
        match rng.gen_range(0..6) {
            0 => "null".into(),
            1 => format!("{}", rng.gen::<bool>()),
            2 => format!("{}", rng.gen_range(-1000..1000)),
            3 => format!("\"{}\"", random_str_content(rng)),
            4 => {
                let n = rng.gen_range(0..5);
                let items: Vec<_> = (0..n)
                    .map(|_| Json::generate(rng, depth + 1))
                    .collect();
                format!("[{}]", items.join(","))
            }
            5 => {
                let n = rng.gen_range(0..5);
                let pairs: Vec<_> = (0..n)
                    .map(|_| format!("\"{}\":{}", random_key(rng), Json::generate(rng, depth + 1)))
                    .collect();
                format!("{{{}}}", pairs.join(","))
            }
            _ => unreachable!()
        }
    }
}
```

### Differential Comparison

```rust
#[test]
fn fuzz_differential() {
    let mut rng = StdRng::seed_from_u64(42);
    let mut parser = Parser::<Json>::new();
    for _ in 0..100_000 {
        let input = Json::generate(&mut rng, 0);
        let ref_result = Json::ref_parse(&input, 0);
        let opt_result = parser.parse(&input);
        assert_eq!(ref_result, opt_result,
            "divergence on input: {input:?}");
    }
}
```

### What This Tests

| Concern | How it's covered |
|---|---|
| Predictive dispatch correctness | Same alternative selected as sequential ordered choice |
| Dyck pairing correctness | Bracket commit points don't cause premature error |
| Eager eviction correctness | Constructed values match deferred construction |
| Memo correctness | Cached results match re-computed results |
| Interaction between optimizations | Any combination that diverges from reference is caught |

### Limitations

- Only tests valid inputs (generated from the grammar).
- Cannot find crashes on malformed input, SIMD boundary errors, or error-path bugs.
- Coverage is bounded by the randomness of generation — pathological structures may be unlikely to appear.

## Approach 2: Coverage-Guided Byte Fuzzing

### How It Works

Coverage-guided fuzzing (cargo-fuzz / libfuzzer) feeds arbitrary byte sequences to the parser and uses code coverage instrumentation to discover interesting inputs:

```
1. Start with a corpus of seed inputs (can include grammar-generated examples).
2. Feed an input to the parser. Instrument which code branches execute.
3. Mutate the input (flip bits, insert bytes, splice, truncate, etc.).
4. If a mutation reaches NEW code branches → keep it in the corpus.
5. Repeat millions of times.
```

The fuzzer does not know the grammar. It discovers structure by observing which mutations reach new code paths. Over time it learns patterns like "byte 0x7B at position 0 reaches more branches" — effectively reverse-engineering the grammar through coverage feedback.

### Setup

```rust
// fuzz/fuzz_targets/parse_json.rs
#![no_main]
use libfuzzer_sys::fuzz_target;

fuzz_target!(|data: &[u8]| {
    if let Ok(input) = std::str::from_utf8(data) {
        let mut parser = Parser::<Json>::new();
        // Must not panic, must not corrupt memory.
        // Result (Ok or Err) is irrelevant — only safety matters.
        let _ = parser.parse(input);
    }
});
```

For differential mode, combine both approaches:

```rust
fuzz_target!(|data: &[u8]| {
    if let Ok(input) = std::str::from_utf8(data) {
        let mut parser = Parser::<Json>::new();
        let ref_result = Json::ref_parse(input, 0);
        let opt_result = parser.parse(input);
        // Both must agree: same Ok value, or both Err
        assert_eq!(ref_result.is_ok(), opt_result.is_ok());
        if let (Ok(r), Ok(o)) = (&ref_result, &opt_result) {
            assert_eq!(r, o);
        }
    }
});
```

### What This Finds That Grammar-Driven Testing Cannot

| Category | Example |
|---|---|
| Crash on invalid input | `[1, 2, ` — truncated input, does eager eviction handle partial state? |
| SIMD boundary errors | 64 bytes of whitespace then `{` — structural scan at block boundary |
| Memo ring buffer collision | Input that causes hash collision at exactly the wrong position |
| Commit-path errors | Dyck bracket opened but close is a different byte — does error path clean up? |
| Integer overflow | Span arithmetic on inputs near `usize::MAX` |
| UTF-8 edge cases | Truncated multi-byte sequences at SIMD block boundaries |

### Comparison

| | Grammar-driven | Coverage-guided |
|---|---|---|
| Input validity | Always valid | Mostly invalid |
| Tests | Correct output (differential) | No crash, no UB, no panic |
| Finds | Logic bugs in optimizations | Edge cases, boundary errors, error-path bugs |
| Coverage | All grammar rules exercised | All code branches exercised |
| Speed | Fast generation, medium parse | Very fast mutation, fast parse |

---

## Combined Strategy

Run both in CI:

1. **Grammar-driven differential**: 100K+ random valid inputs per test run. Catches optimization logic bugs.
2. **Coverage-guided byte fuzzing**: continuous or nightly runs, hours of fuzzing time. Catches crash bugs, boundary errors, and edge cases.
3. **Seed cross-pollination**: use grammar-generated inputs as initial seeds for the coverage-guided fuzzer. The fuzzer then mutates them to explore invalid/boundary territory that pure generation would never reach.

The reference parser is the single source of truth. Any divergence — wrong result, crash on input the reference handles, accept/reject disagreement — is a bug in the optimizations.
